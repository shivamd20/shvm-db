Why this exists

One page on the motivation behind the experiment.

DynamoDB gets a lot of throughput. A lot of that comes from partitioning, routing, and operational discipline, not from a special storage engine. I wanted to see how much of that model I could rebuild with pieces I could actually run and measure.

Why rebuild a DynamoDB-like API?

So I could see where the bottlenecks are. Once you route by partition key, run one writer per partition, and put SQLite behind it, you get a clear mental model. No hidden caches, no magic. The goal was to get exact PutItem/GetItem/UpdateItem/DeleteItem semantics and strong per-partition consistency, then benchmark and iterate.

Why Cloudflare Durable Objects?

Each DO has a single-threaded, single-writer guarantee. That maps cleanly to one partition = one writer. I didn't have to build coordination; the runtime gives it. The question was: how far can DOs scale for this kind of workload? This project is an attempt to answer that, not to sell a product.

Why this stack?

SQLite per partition: simple, debuggable, and the only source of truth in the MVP. Queues for replication so reads can fan out to replicas. R2 is in the roadmap for durability and recovery, but the current experiment runs without it. The idea was to keep the pipeline understandable so that when numbers change, I know why.

What this is not

It is not a DynamoDB replacement. It is not tuned for production. There is no LSI/GSI, no automatic partition splitting, no multi-region. Hot partitions hit a hard ceiling. The point is to learn how the architecture behaves, not to ship it as a service.

For the longer story and how the system evolved, see the experiment blog.
