DynamoDB-style API on Durable Objects

Same PutItem/GetItem/UpdateItem semantics, one writer per partition, SQLite under the hood. I built it to see where the bottlenecks are.

See benchmarks Try it



v0.2.0. Experiment, not for production.

What it is

One partition key maps to one Leader Durable Object; read replicas when load spikes. No hidden caches — SQLite is the only source of truth. PutItem, GetItem, UpdateItem, DeleteItem.

Limitations

No LSI/GSI, no automatic partition splitting, no multi-region. Hot partitions hit a hard ceiling. Full list on GitHub.

Leader

All writes go to one Leader. It assigns a monotonic version and appends to an immutable log.

Standby

Consumes full history. Onboards new replicas by streaming backfill from Standby.

Replicas

When read load exceeds a threshold, new replicas are provisioned; they backfill then serve traffic.

Ordering and replicas

No wall clocks. Every mutation gets a monotonic version from the Leader; replicas apply in strict order so time never moves backwards. Replica lifecycle: CREATED → BACKFILLING → CATCHING_UP → READABLE. Each replica stores lastAppliedVersion so the system stays robust to crashes and reordering.

Why and how it evolved

DynamoDB gets a lot of throughput from partitioning, routing, and discipline — not a special storage engine. I wanted to see how much of that I could rebuild with pieces I could run and measure. So I could see where the bottlenecks are. One writer per partition, SQLite behind it, no hidden caches. Why Durable Objects? Each DO has a single-writer guarantee; that maps to one partition = one writer. I didn't have to build coordination; the runtime gives it. This project is an attempt to see how far DOs can scale for this workload, not to sell a product.

Started with a single DO and SQLite. Then table metadata, replication over queues, UpdateItem, YCSB benchmarking and the benchmark-logs page. TraceDO and routing cache followed; table-metadata caching in the request path helped. Observability improved with trace events. Workload sizes were reduced so runs finish in a reasonable time.

What I learned: hot partitions cap throughput — one writer means one serialized write stream. Routing and metadata caching removed a lot of lookups. The trace viewer made it possible to see where time was spent. I still don't have a clean answer to "how far DOs can scale" but the numbers below are the current snapshot.

What this is not: not a DynamoDB replacement, not tuned for production. No LSI/GSI, no partition splitting, no multi-region.

How the numbers are produced

YCSB runs live in benchmarks/workloads/. Run npm run benchmark:run (local) or npm run benchmark:live. Raw output goes to benchmarks/results/run_<timestamp>/. benchmarks/process_results.py parses the run files and writes public/benchmarks/<timestamp>/results.json and updates public/benchmarks/index.json. The Benchmark Logs page and the cards above read from that. So the source of truth is whatever is in public/benchmarks/ after your last run.

Traces

Every request has an ID. In the Playground, send a request and use “View trace”, or open the Trace page and enter a request ID. You get a timeline of events for that request.
