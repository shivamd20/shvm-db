DynamoDB-compatible API on Durable Objects

An experiment to see how far DOs can scale. Same PutItem/GetItem/UpdateItem semantics, one writer per partition, SQLite under the hood. Why this exists.

Docs Architecture
v0.2.0 (Replication). Experiment, not for production.

What it does

DynamoDB gets its throughput from partitioning and single-writer discipline. shvm-db rebuilds that model: exact PutItem, GetItem, UpdateItem, DeleteItem semantics; one partition key maps to one Leader Durable Object; read replicas when load spikes; no hidden caches, SQLite is the only source of truth.

Limitations (MVP)

No LSI/GSI, no automatic partition splitting, no multi-region. Hot partitions hit a hard ceiling. See the README for the full list.

Leader-Follower Architecture

The system uses a Leader-Standby-Replica model: one writer per partition, replicas consume the log and serve reads.

Leader (Writes)

All writes go to a single Leader. It assigns a monotonic version number and appends to an immutable log. This guarantees strong consistency.

Standby (History)

A Standby node consumes the full history. It is responsible for onboarding new replicas by streaming historical backfill data.

Autoscaling Replicas

If read load exceeds capacity, the system automatically spawns new Replicas defined by the cursor model. They backfill from Standby and then serve traffic.

Distributed Systems Reality

Tradeoffs are explicit. The system does not use wall clocks for ordering. Every mutation gets a monotonic integer version from the Leader. Replicas apply updates in strict order so time never moves backwards.

Backfill & Migration

Replica provisioning is handled by a state machine: CREATED → BACKFILLING → CATCHING_UP → READABLE. Only when a replica is fully caught up does it serve traffic.

Cursor Model

Replicas store a single cursor: lastAppliedVersion. This makes the system robust against crashes, duplicates, and reordering.
