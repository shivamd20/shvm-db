The Vision

DynamoDB scales to absurd throughput not because of magic, but because of brutal operational discipline. shvm-db forces you to understand these physics by rebuilding them yourself.

Core Principles

  • Exact Parity: PutItem, GetItem, Query—same semantics, same constraints.
  • Single Writer: One partition key maps to exactly one Leader Durable Object.
  • Read Replicas: Automatically provisions read-only replicas when load spikes.
  • Zero Layers: No hidden caches. SQLite is the only source of truth.

Leader-Follower Architecture

We use a strict Leader-Standby-Replica model to guarantee consistency while enabling massive read concurrency.

Leader (Writes)

All writes go to a single Leader. It assigns a monotonic version number and appends to an immutable log. This guarantees strong consistency.

Standby (History)

A Standby node consumes the full history. It is responsible for onboarding new replicas by streaming historical backfill data.

Autoscaling Replicas

If read load exceeds capacity, the system automatically spawns new Replicas defined by the cursor model. They backfill from Standby and then serve traffic.

Distributed Systems Reality

Building a database at scale means choosing your tradeoffs explicitly. Here is how shvm-db handles the hard stuff.

Consistency via Monotonicity

We don't use wall clocks for ordering. Every mutation is assigned a strict monotonic integer version by the Leader. Replicas apply updates in strict order, guaranteeing that time never moves backwards.

Backfill & Migration

Replica provisioning is handled by a state machine: CREATED → BACKFILLING → CATCHING_UP → READABLE. Only when a replica is fully caught up does it serve traffic.

Cursor Model

Replicas store a single cursor: lastAppliedVersion. This makes the system robust against crashes, duplicates, and reordering.
