Experiment log

How the project evolved, what the benchmarks measure, and what I learned. For motivation, see why this exists.

How it evolved

Started with a single Durable Object and SQLite. Then table metadata, LRU and Bloom filter caching, and validation. After that came async replication and read distribution over queues so replicas could serve reads. UpdateItem landed next, then the YCSB-based benchmarking setup and the benchmark-logs page. TraceDO and routing cache followed; so did smart placement in Wrangler config and table-metadata caching in the request path. Observability got better with trace events and error handling in TraceDO. Workload sizes were reduced so runs finish in a reasonable time.

Workloads

Three YCSB variants live in benchmarks/workloads/. What each does:

  • Variant A (Hot Partition Stress): 500 records, 3k operations, 40% read / 40% update / 20% insert, Zipfian 0.99, 8 threads. Pushes a small key set hard.
  • Variant B (Sustained Mixed Load): 2k records, 8k operations, 60% read / 25% update / 15% insert, latest distribution, 6 threads. Mix of read and write over a larger set.
  • Variant C (Concurrency Scaling): 1.5k records, 6k operations, 80% read / 15% update / 5% insert, uniform distribution, 4 threads. Read-heavy, spread across keys.

Run them locally with npm run benchmark:run (default endpoint http://localhost:8787/api) or against the live site with npm run benchmark:live. Raw YCSB output goes into benchmarks/results/run_<timestamp>/; process_results.py parses it and writes public/benchmarks/<timestamp>/results.json and updates public/benchmarks/index.json.

Observability

Every request can be inspected by request ID. In the Playground, send a DynamoDB-style request and use "View trace" to open the trace viewer, or open trace.html and enter a request ID. The backend calls TraceDO and returns a timeline of events for that request.

What I learned

Hot partitions cap throughput: one writer per partition means one serialized write stream. Routing cache and table-metadata caching removed a lot of repeated lookups and helped. The trace viewer made it possible to see where time was spent when something was slow. YCSB is a blunt instrument but good enough to compare runs; the three variants give a rough read on skew vs mixed vs read-heavy. I still don't have a clean answer to "how far DOs can scale" but the numbers above are the current snapshot.

How this doc is built

The performance table and the Benchmark Logs page both use data from public/benchmarks/<run_id>/results.json. Those files are produced by benchmarks/process_results.py, which reads YCSB's CSV-style summary lines from the run_*.txt files and aggregates them. When you run npm run benchmark:run, the script copies results into public/benchmarks/ and updates index.json. So the single source of truth for "current" numbers is whatever is in that folder after your last run.
