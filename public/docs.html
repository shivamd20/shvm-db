Quickstart

All requests to shvm-db follow the DynamoDB JSON protocol. You can use any standard HTTP client or the official AWS SDK.

Using cURL

# Create an item
curl -X POST https://shvm-db.workers.dev/api \
  -H "x-amz-target: DynamoDB_20120810.PutItem" \
  -H "Content-Type: application/x-amz-json-1.0" \
  -d '{
    "TableName": "Users",
    "Item": {
        "PK": {"S": "user_1"},
        "SK": {"S": "profile"},
        "name": {"S": "Alice"}
    }
  }'

Roles & Replication

shvm-db uses a Leader-Standby-Replica architecture to provide strong consistency for writes and massive scalability for reads.

Leader

Every partition has exactly one Leader. All writes (PutItem, DeleteItem) communicate strictly with the Leader. The Leader assigns a Monotonic Version to every mutation and persists it to an immutable log.

Standby

A Standby node consumes the replication stream from the Leader. It maintains the full history of all versions. Its primary job is to serve as a designated source for Backfill operations when new Replicas are provisioning.

Read Replicas

Replicas are ephemeral copies of the data. They consume the live stream from the Leader and backfill history from the Standby. Read requests (GetItem) are load-balanced across all available Replicas in the READABLE state.

Autoscaling

shvm-db automatically scales read capacity based on traffic.

  • Monitoring: The PartitionDO tracks request rates in real-time.
  • Trigger: When load exceeds a threshold, the system triggers the provisionReplica workflow.
  • Scale Up: A new Durable Object is created, it backfills from Standby, and once caught up, it joins the routing table.
  • Zero Downtime: The system continues to serve reads from existing replicas while new ones are provisioning.

Comparison to DynamoDB

While inspired by DynamoDB's data model, shvm-db makes different trade-offs to prioritize explicit behavior and cost control.

Feature shvm-db DynamoDB
Replication Leader-Standby-Replica (Explicit) Hidden (Multi-AZ)
Consistency Strong (Monotonic Versioning) Eventual (default) or Strong
Scaling Dynamic Read Replicas Partition splitting
Cost Model Per Request / DO Time RCU / WCU or On-Demand

MVP Limitations

  • Single Table: Currently supports a single logical table.
  • No Query Support: Query operations are not yet implemented. Use GetItem for point lookups.
  • Static Partitioning: While Replicas scale, the Partition Keys are routed via consistent hashing (currently simplified to 1 partition for MVP).

Consistency Model

shvm-db guarantees that time never moves backwards.

Read-After-Write Consistency

By default, reads may be served by a slightly lagging Read Replica (Eventual Consistency). However, because versions are monotonic, a client can track the lastSeeVersion to ensure they never see stale data compared to their own history.

Monotonicity

Even if you read from different replicas, you made see older data if you switch to a more lagging replica, but the system state converges to the Leader's strict order.
